Concept central

Qu'est-ce qu'un Application Skeleton

Un Application Skeleton n'est ni une app de démo ni un dossier de templates : c'est une base architecturale pré-assemblée pour un produit. Gridfin fixe le stack, la structure, les règles, la stratégie de tests et les quality gates avant que Claude Code n'écrive les premières features.

Architecture

Le stack, les couches, les frontières d'imports et les règles de changement sont déjà choisis, pour que l'agent ne réarchitecture pas le projet à chaque feature.

Spécifications

Le travail commence par un PRD et des specs de features : d'abord on sait ce qu'on construit, ensuite le code apparaît.

Vérifications

Tests, lint, e2e et build tournent comme un seul quality gate, pour que l'erreur soit visible avant le merge.

Processus

Les skills et les playbooks mènent le développement dans un cycle répétable : idée → spec → code → tests → review → deploy.

Ce que tu obtiens

Playbooks

Des scénarios pas à pas pour le déploiement, l'analytics, le pricing, la conformité et d'autres tâches d'ingénierie où la mémoire de session ne suffit pas.

Skills

Des workflows d'agent pour l'onboarding, les features, le design, la review, la vérification, les déploiements, les mises à jour et la capture des learnings.

Règles d'ingénierie

Les règles d'architecture, de frontend, de tests, de sécurité, de documentation et de process git que suit l'agent.

Quality gates

Un seul passage de lint, tests, e2e et build montre le rouge avant le merge, pas après la release.

Documentation

PRD, specs, ADR, playbooks et règles gardent le contexte entre les sessions, pour que l'agent ne reparte pas de zéro chaque jour.

Pourquoi pas juste Claude Code ?

Claude Code seul écrit du code, mais ne donne pas de processus d'ingénierie stable. Sans Gridfin, chaque session redécide comment construire le projet ; avec Gridfin, l'agent travaille selon des specs, des règles, des hooks, des tests et des quality gates impossibles à contourner en silence. L'analyse complète : pourquoi le développement avec l'IA a besoin de règles d'ingénierie.

En quoi c'est différent d'un boilerplate — ShipFast et les autres ?

Les boilerplates vendent du code pré-assemblé que tu personnalises. Gridfin est un starter kit agent-native : un squelette léger plus un processus qui spécifie, construit et teste ton produit spécifiquement. Tu ne découpes pas le dashboard de quelqu'un d'autre — tu fais grandir le tien.

Qu'est-ce qu'un Application Skeleton ?

Un Application Skeleton est la base architecturale sur laquelle Claude Code construit votre produit. Ce n'est pas un simple template de projet : les décisions d'ingénierie sur le stack, la structure, les tests et la CI sont déjà prises, et la suite du développement passe par les specs, les skills et les quality gates. Le détail complet : qu'est-ce qu'un Application Skeleton.

En quoi c'est différent de MakerKit et Supastarter ?

MakerKit et Supastarter sont des boilerplates SaaS complets avec des instructions pour agents et un support de tests. Gridfin résout un autre problème : il part de votre idée et exécute un processus guidé par les specs, avec des Hooks qui bloquent les violations connues, des tests dont l'échec doit être prouvé et un gate ledger qui indique si le changement est prêt. Choisissez-les pour des fonctions SaaS préconstruites ; choisissez Gridfin pour un processus de développement imposé autour d'un produit ciblé.

Pourquoi la stack est-elle fixe ?

Parce que tout le processus — règles, hooks, tests, gates, playbooks — est éprouvé exactement sur cette stack : Next.js + TypeScript, Tailwind + shadcn/ui, Postgres. La liberté de choisir une stack, c'est quarante décisions de plus que tu devrais prendre sans l'expérience.

Puis-je utiliser ma propre stack ?

Non — et c'est voulu. Gridfin n'est pas un kit où tu choisis ta stack : retire la stack fixe et tout ce qu'elle soutient disparaît — les règles éprouvées, les tests et les gates. Si tu as besoin d'une autre stack, la réponse honnête est : Gridfin n'est pas ton outil.

De quoi ai-je besoin pour exécuter Gridfin ?

Il faut Claude Code, Git, un terminal et la toolchain Node.js/pnpm prise en charge. Gridfin s'exécute localement comme repository git et ne demande ni compte Gridfin hébergé ni runtime propriétaire.

Et si le projet arrête d'être développé ?

Rien de grave : le repository est à toi, le code et le processus fonctionnent localement et ne dépendent pas de l'existence de Gridfin en tant que produit. Les mises à jour s'arrêteraient — tout le reste demeure.

Est-ce adapté à un débutant ?

Si tu es prêt à travailler avec un terminal, git et Claude Code en suivant des instructions pas à pas — oui : la box porte l'architecture, la stratégie de tests et le contrôle qualité pour toi. Si tu vois un terminal pour la première fois — commence par Lovable ou Bolt.

Comment Gridfin empêche-t-il l'IA de casser le projet ?

Gridfin rend l'erreur visible avant le merge : chaque changement passe lint, tests, e2e et build, et les règles sont imposées par les hooks et les quality gates. L'agent peut écrire du code vite, mais il ne peut pas livrer un changement sans les vérifications.
